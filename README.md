# CardBot

**一套任务贯穿早晚；每封草稿都有依据。** 这是面向全球贸易团队的客户开发与邮箱协作工作台。

- 当前公开 Demo：<https://opc8838-hub.github.io/cardbot/>
- 旧版单文件 HTML：<https://opc8838-hub.github.io/cardbot/archives/cardbot-visual-v2.html>
- GitHub 仓库：<https://github.com/opc8838-hub/cardbot>
- 当前状态与测试：[docs/STATUS.md](docs/STATUS.md)

公开 Demo 是静态交互预览，使用虚构数据，不要求账号或 API。它可以说明产品流程和界面，但**不是已经接通 DeepSeek、邮箱、小满 OKKI、微信、飞书或 WhatsApp 的线上业务系统**。

## CardBot 解决什么问题

CardBot 把两条经常断开的工作线放进同一个工作台：

1. **开发新客户**：确定目标企业，查企业背景和联系人来源，判断是否值得联系，AI 准备开发信，人确认后再进入草稿记录。
2. **服务现有客户**：接住邮件或渠道消息，先看历史和公司资料，再判断下一步，AI 起草回复，人确认后再保存或发送。

两条线最后共用同一套受控流程：

```text
客户发来消息 / 找到潜在客户
            ↓
客户线：先看以前谈过什么、这个客户是谁
            ↓
知识检索：只引用当前人员有权看的企业资料
            ↓
任务判断：判断现在该做什么、谁来做、什么时候做
            ↓
草稿审批：AI 先写，人确认后再发
            ↓
审计：记录依据、修改、审批、保存或发送结果与责任人
```

微信、飞书、WhatsApp、邮箱只是不同入口；业务规则、知识权限、审批和审计应由 CardBot 后端统一执行，不为每个渠道重新做一套产品。

## 公开 Demo 已经实现

### 演示与视觉

- 多语言问候、用户提供的卡牌视频、同尺寸翻卡登录、英文默认功能页和工作台。
- 深浅主题与中英文采用渐变过渡；系统强调色统一为紫色，渠道品牌色和用户 Bot 自选色保留。
- 20 秒无操作进入文字地球屏保；顶部纯图形按钮可立即预览，点击屏保任意位置返回工作台。
- 桌面与移动宽度适配；顶部遮挡、圆角、按钮居中、紧凑卡片和可拖拽 Bot 等细节已有自动化覆盖。

### 客户开发线

- 目标客户、企业发现、背景研究、匹配与时机判断、负责人/来源、合作切入点、开发信草稿六阶段。
- 虚构潜客资料、联系人来源、推荐理由和风险提示。
- 开发信复用统一的人工核对、审核、保存记录和审计摘要。

### 现有客户与邮箱协作线

- 今日任务、客户与历史邮件、事实依据、下一步判断、回复草稿、人工审核、草稿记录和团队汇总。
- 修改草稿后审核失效；未勾选核对项不能通过审核。
- 支持模拟保存成功、保存失败、保留内容、重新审核和刷新后本地持久化。

### 演讲与渠道展示

- 十步业务演练：当前功能按顺序紫色高亮，支持暂停、继续、上一步、下一步、跳步、重播和退出。
- “手机远程设置”提供六页简洁演讲视图，说明统一入口、客户开发、客户跟进、受控 AI、审批与审计。
- 微信、飞书、WhatsApp 使用真实品牌 Logo 的界面展示，但二维码、机器人、Webhook 和远程会话目前均是本地预览。
- 个人 CardBot 可选表情和颜色；聊天窗口支持拖动、缩小、关闭和预置知识问答。

### 现有工程基座

- TypeScript、Vite、Express、Zod、测试脚本和 GitHub Actions 持续检查。
- 后端已有 AI 模型运行时、邮件 EML 解析、审核/草稿领域基础、OKKI 连接器接口、队列和部分 CRM 基础。
- `/crm.html` 保留原 CRM 原型入口，但它依赖后端、数据库和登录配置，不属于公开静态 Demo 的已上线能力。

## 功能边界：哪些是真的，哪些还是演示

| 能力 | 当前事实 | 生产版还缺什么 |
| --- | --- | --- |
| 界面、动效、演练 | 已实现，可在公开 Demo 直接体验 | 真实数据回归与更多浏览器验收 |
| 客户开发流程 | 已实现虚构样例和本地状态 | 企业数据源、合规联系人来源、查重、分配与正式 API |
| 历史邮件/客户线 | 已有界面、样例和本地 EML 解析基础 | 授权邮箱增量同步、客户归并、附件处理和服务端存储 |
| 知识检索 | 只有预置问答和规划页 | 文档摄取、向量/全文检索、来源引用、版本与权限过滤 |
| 任务判断 | 规则和演练已呈现 | DeepSeek 结构化判断、后端校验、队列、失败回退和人工改派 |
| 草稿审批 | 本地审核门槛与状态流已实现 | 服务端审批、身份签名、并发控制、真实草稿读回验证 |
| 审计 | 本地记录与演示摘要 | 不可篡改的服务端日志、留存策略、导出和管理员检索 |
| DeepSeek | 已选技术方向，后端有兼容运行时 | API Key、模型/额度、提示词与结构化输出、限流、脱敏和评测 |
| 小满 OKKI | Mock 和适配器接口存在 | 企业 `client_id/client_secret`、scope、字段映射及草稿相关端点/授权 |
| 邮箱 | 可解析本地 EML | IMAP、Microsoft Graph 或 Gmail API 授权；增量同步与受控发送 |
| 微信/飞书/WhatsApp | 界面和统一能力说明 | 各平台企业应用、Webhook、签名校验、消息卡片、回调与审核 |
| 多用户隔离 | Demo 可切换虚构角色 | 正式登录、租户/部门/用户映射、行级权限和密钥隔离 |
| 对外发送 | **不会真实发送** | 人工审批后的发送适配器、幂等、防重复、撤销/补偿和送达回执 |

### 明确不会做的事

- 不让模型像通用聊天机器人一样无边界回答。正式 Bot 只开放客户、知识、任务、草稿和审计相关意图；超出范围直接拒绝或引导回功能菜单。
- 不让 AI 绕过人工审批自动给客户发信。
- 不把邮件里的指令当系统指令，不让一个业务员检索另一个业务员无权查看的数据。
- 不把界面上的“已连接”“已保存”演示状态冒充真实外部系统验收结果。
- 不把账号、密钥、真实邮件、数据库和浏览器登录会话提交到 Git。

## 要变成真实产品，还需要哪些 API 和基础设施

### 1. 身份、租户与权限

- 企业、部门、业务员、经理和管理员账号体系。
- 登录/OAuth、会话管理、密码策略或企业单点登录。
- 每个用户到邮箱、OKKI 用户和渠道账号的映射。
- 服务端行级权限：客户、邮件、知识文档、任务和草稿都按租户与用户过滤。

这一步解决“每个业务员只看到自己的客户线与任务”，避免不同人员的上下文和数据串在一起。

### 2. DeepSeek 模型服务

- 服务端配置 `baseUrl`、`apiKey`、模型 ID、额度和网络出口，密钥不得放前端。
- 固定结构化输出：使用了哪些事实、缺哪些事实、建议任务、草稿、风险标记。
- 对模型输入做权限过滤、敏感信息脱敏、提示注入防护和长度限制。
- 对输出做引用验证、价格/交期等关键字段校验、超时/重试/回退、成本统计和质量评测。

### 3. 企业知识库

- 接入产品资料、样品政策、报价规则、交期、合同模板和历史沟通。
- 文档解析、分段、索引、版本、过期标记、来源链接和访问权限。
- 找不到可靠依据时回答“不知道/需要确认”，不能让模型用常识补写企业政策。

### 4. 邮箱与客户数据

- 选择 IMAP、Microsoft Graph、Gmail API 或企业现有邮件 API；准备 OAuth/应用密码及管理员授权。
- 增量同步邮件、线程归并、附件扫描、客户去重和失败重试。
- 写草稿、读回核对、人工批准后发送、幂等键、发送结果和退信回执。
- 客户开发还需要合法的企业/联系人数据源、邮箱验证服务和来源证明；“找到邮箱”不是完整客户开发。

### 5. 小满 OKKI

- 企业主账号在开放平台创建应用并提供 `client_id/client_secret` 与所需 scope。
- 确认客户、联系人、线索、商机、任务、历史邮件和邮件草稿的真实端点及字段。
- 若官方 API 不覆盖草稿，需要主办方/企业书面允许后，再评估隔离 RPA；只保存并读回草稿，绝不自动点击发送。

详见 [OKKI 接入计划](docs/OKKI_INTEGRATION_PLAN.md) 和 [接入缺口](docs/INTEGRATIONS.md)。

### 6. 飞书、微信与 WhatsApp

- 飞书企业自建应用、机器人/Webhook、事件订阅、签名与消息卡片。
- 微信应先明确是企业微信、微信公众号还是个人微信；生产集成只走平台允许的企业接口。
- WhatsApp Business Platform 应用、号码、模板审批、Webhook 和会话窗口规则。
- 三个渠道只负责收消息、通知和轻量操作；完整历史、复杂编辑和管理员配置仍在 CardBot 工作台完成。

### 7. 生产运维与安全

- PostgreSQL/MySQL、对象存储、Redis/任务队列、备份与恢复。
- HTTPS 域名、后端部署、环境变量/密钥托管、日志脱敏、监控告警。
- Webhook 重放保护、速率限制、审计留存、数据删除、隐私与跨境数据合规。
- 单元、集成、权限、模型评测和真实连接器沙箱测试。

## 旧版 HTML 如何保存

旧版不是截图，也不是当前页面的复制品。仓库固定保存 [archives/cardbot-visual-v2.html](archives/cardbot-visual-v2.html)，来源提交为 `c3caa2fcdca0f7959df4c064ad6cc8519519627c`。它把样式、脚本和地球数据全部内嵌，一个文件即可离线打开，并使用 `cardbot_archive_v2_` 独立存储键，不会覆盖当前工作台数据。

公开部署时，GitHub Actions 会把这个 HTML 单独复制到 `archives/` 路径，所以新版与旧版都有各自链接。版本边界、离线行为和重新生成方法见 [archives/README.md](archives/README.md)。

## 本地运行

需要 Git 与 Node.js 24（当前实测 v24.12.0）：

```sh
git clone https://github.com/opc8838-hub/cardbot.git
cd cardbot
npm ci
npm run preview:dev
```

打开 <http://127.0.0.1:5190/>。第一次进入会播放完整开场；访问 `/?intro=1` 可强制重播。

## 测试与构建

```sh
npm run test:core
npm run build --workspace frontend
```

浏览器回归需要 Python Playwright/Chromium，并在另一个终端保持 `npm run preview:dev` 运行：

```sh
npm run test:preview-ui
```

每次推送 `main` 后：

- `.github/workflows/webpack.yml` 运行核心测试与前端构建。
- `.github/workflows/pages.yml` 重新构建并发布当前 Demo 与旧版 HTML。
