# 模型、API、开源组件与接入缺口

## 先用大白话说明

API 是两个系统交换数据的约定入口。**模型 API、小满 API、邮箱协议是三回事**：买了 DeepSeek 不会自动获得小满权限，有了小满网页账号也不等于能调小满 API。

当前新预览不需要任何付费模型，因为它展示的是固定模板和虚构数据。后续使用 DeepSeek 的云接口时，通常不需要你本地买显卡；但必须有账号、可用额度、服务器网络与受控的密钥配置。最终模型名称、价格与接口以配置当日官方文档为准，本文不锁死可能变化的价格。

## DeepSeek：已选方向，尚未真实接入

用户决定使用 DeepSeek，以成本为优先，但暂不接入。既有 `backend/src/ai-model-runtime.ts` 支持 `openai-compatible` 协议，可发送 `/chat/completions` 请求；配置类型包含 baseUrl、apiKey、模型配置等。这个基础可以复用，不需要把整套 CRM 换框架。

**目前没有“填一个 DEEPSEEK_API_KEY 就自动完成整条链路”的实现。** 新 UI 没有调用模型；不能把 `.env` 多写一个变量当作功能完成。

接入时至少完成：

1. 从供应商官方文档确定 base URL、模型 ID、协议和费用，配置在服务端。
2. 将客户原文、历史事实、未确认项分开提供，要求结构化返回：subject/body/usedFactIds/missingFacts/riskFlags。
3. 后端验证引用 ID 确实来自当前客户授权材料，价格/交期/赔偿不能靠模型自行推断。
4. 原始邮件视为不可信数据，邮件中的“忽略规则”等指令不能改变系统权限或泄露其他客户数据。
5. 加超时、限额、输入长度、重试策略、失败回退、成本计量与日志脱敏。
6. 显式保留人工审核门槛；修改正文后审核失效，真实外写前再检查状态。
7. 用脱敏样例跑模型测试，检查幻觉、不完整历史、多语言、冲突约定、超时；再绑定新工作台。

## 小满 OKKI：三种方式现状

| 模式 | 当前代码做什么 | 缺什么 |
| --- | --- | --- |
| Mock | 返回模拟健康与模拟保存回执 | 没有真实小满存储；只用于开发 |
| official_api | 读取配置，向配置路径发通用 Bearer POST | 官方文档、真实鉴权协议、字段、权限、限流、草稿读写端点测试 |
| playwright_rpa | 接受一个可注入 driver；缺 driver 时提示未就绪 | 授权账号、允许自动化、独立 Worker、选择器、登录/验证码流程、重试和读回 |

统一接口当前只有 `health()` 和 `saveDraft()`。health 的“已配齐”不能写成“已认证/已保存”。后续需要 `readDraft`、`verifyDraft` 等职责，或者独立验证器。

相关环境变量已在根 `.env.example`：

```dotenv
OKKI_CONNECTOR_MODE=mock
OKKI_API_BASE_URL=
OKKI_API_TOKEN=
OKKI_DRAFT_API_PATH=
```

这些空值是待配置，不是秘密资料的缺失副本。不要猜端点，不要把网页路径直接当 API，更不能绕开验证码或企业权限。主办方给账号后优先询问官方草稿读写权限；如果没有对应 API，再在明确允许的条件下做浏览器自动化。

### 给主办方的询问清单（可直接发送）

1. 能否提供独立测试企业/租户及业务员、管理员两类账号？我们不会自动发送邮件。
2. 网页权限与 API 权限是否分别开通？是否有官方开发文档、应用凭证和测试环境？
3. 是否开放客户、联系人、历史邮件读取，以及草稿创建、更新、列表和详情读取？
4. 鉴权方式是什么：OAuth、签名、token 或其他？token 时效、刷新、IP 白名单、限流如何处理？
5. 能否提供脱敏历史往来、产品资料、报价/交期/客诉样例以及正确答案边界？
6. 如 API 不覆盖草稿，是否允许 Playwright 操作测试账号？验证码/二次验证由人协助是否可接受？
7. 演示时能否退出再登录以验证草稿持久化？草稿保存失败或重复写入如何处理？
8. 赛事是否要求线上部署、演示录屏、源码公开、提交截止和特定安全/隐私限制？

## 邮箱：读取与解析不要混为一谈

- 已用 PostalMime 把本地 RFC822/EML 解析为邮件信息，后端已有测试。
- **ImapFlow 尚未安装/接线**。它未来可用于获授权 IMAP 邮箱增量读取，需要服务器、端口、TLS、账号/应用密码/OAuth、文件夹、UID 增量策略。
- **mailparser 尚未安装**。目前已有 PostalMime，不应为了“都采纳了”重复加入两套解析器，除非有明确 MIME/附件需求和测试证明。
- Nodemailer 在既有后端依赖中，但本赛题新链路不应调用它自动发信。
- 真实附件需要扫描/大小上限/类型限制/脱敏与存储隔离；OCR 与产品知识引用另行验收。

## 开源组件采用表

| 组件 | 采用状态 | 用途 |
| --- | --- | --- |
| TypeScript / Vite | 已有并继续使用 | 前端构建、类型检查 |
| Express / Zod | 已有并继续使用 | 后端与输入校验 |
| postal-mime | 已引入、测试通过 | EML 解析，不是邮箱连接 |
| d3-geo / topojson-client / world-atlas | 已有依赖、本次复用 | 真实大陆几何与小字地球 |
| Playwright | 本次用于浏览器测试；小满 RPA 待实现 | UI 自动化不等于小满驱动 |
| BullMQ / Redis | 旧工程具备队列基础 | 后续长任务/RPA Worker，可选依赖 |
| ImapFlow / mailparser | 未引入 | 早期候选，不是假装已经采用 |
| LangChain / n8n 等大型编排 | 未为本次额外引入 | 优先复用已有 Agent runtime，避免多套状态系统 |

精确版本以两个 lockfile 为准；授权说明见 THIRD_PARTY_NOTICES。代码可用、许可合规、账号权限、真实业务稳定性需要分别检查。

## 业务 Agent skills

仓库已保留 `daily-work-loop`、`evidence-email-drafting`、`okki-draft-delivery` 以及原有 consultation/outreach/prospecting 等技能包。它们是本项目 Agent 的流程知识，和开发电脑里给 Codex 使用的设计/测试技能不是同一个层次。换账号后不应依赖旧电脑的个人技能目录才能跑项目。

本次开发使用前端设计与浏览器测试技能指导了版式与验收；运行 CardBot 本身不要求安装这些个人开发技能。业务能力最终仍由代码、授权数据和测试保证。
