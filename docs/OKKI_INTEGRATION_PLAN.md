# 小满 OKKI 最终打通方案

日期：2026-09-12。本文只记录可验证事实与下一步，不保存账号、密码、Cookie、客户名称、联系人或邮件正文。

## 结论

小满有官方开放 API，但“能登录网页”与“能调用 API”是两套权限。目前官方公开资料可以支持客户、线索、商机、用户、报表等数据接入；本次没有找到公开的历史邮件读取或邮件草稿保存/读回端点。因此最终闭环按 **API 优先、RPA 补位、人工审核不取消** 实现。

```text
历史邮件/客户事实
        ↓
事实提取与缺失项标记
        ↓
DeepSeek 生成候选草稿（后续接入）
        ↓
人工核对收件人、正文、承诺
        ↓
统一 OkkiConnector
   ├─ Official API：有正式端点就走 API
   └─ Playwright RPA：API 不覆盖草稿时补位
        ↓
草稿箱读回比对 → 退出/重新登录 → 再次读回
```

## 官方 API 路线

1. 由主办方或企业主账号在“企业管理 → 外部对接 → API 对接”开通赛事应用。
2. 通过安全渠道配置应用凭证到后端密钥管理；不写前端、不写日志、不进 Git。
3. 后端用 `client_credentials` 获取短期 access token，实现自动刷新、超时、限流、租户隔离和脱敏审计。
4. 先接只读能力：当前用户、客户、联系人、线索、商机和任务；逐项以官方 scope 和实际响应验收。
5. 单独向主办方确认邮件历史和草稿的创建、更新、列表、详情权限。只有获得正式文档并实测成功，才把它标为官方 API 能力。

## Playwright RPA 补位路线

RPA 只在官方 API 不覆盖邮件草稿、且主办方明确允许网页自动化时启用。它运行在后端独立 Worker 中，不进入前端请求主线程，也不直接复用个人日常浏览器资料目录。

一次保存必须形成完整回执：

1. 检查登录态；验证码或二次验证交给人处理，不绕过。
2. 打开邮件模块，按稳定 ID/邮箱定位授权测试客户与历史会话。
3. 点击回复或新建，填入收件人、主题、正文。
4. 最终写入前再次检查人工审核版本和幂等键；绝不点击发送。
5. 保存草稿，进入草稿箱，以唯一业务键或主题查回。
6. 读取收件人、主题、正文，规范化后计算哈希并与待写版本比较。
7. 退出并重新登录，再查一次同一草稿，证明不是仅存在页面内存。
8. 返回 `remoteDraftId/保存时间/校验哈希/截图证据引用`；截图和日志必须脱敏。

选择器优先使用可访问角色、稳定属性和业务 ID，中文按钮文本只作降级方案。页面改版、网络超时、重复保存、登录失效都必须显式失败，不能把“点击过”当“保存成功”。

## 统一连接器需要补的代码

现有接口只有 `health()` 和 `saveDraft()`，后续至少扩展：

- `authenticate()`：获取/刷新授权状态；
- `saveDraft(input, idempotencyKey)`：幂等保存；
- `getDraft(remoteDraftId)`：读回草稿；
- `verifyDraft(expected, actual)`：逐字段和哈希比对；
- `verifyAfterRelogin(remoteDraftId)`：新会话持久化复核；
- 明确回执状态：`mock/local/remote_saved/remote_verified/failed`，UI 不混淆。

## 真实验收前还缺什么

1. 主办方确认 API 对接权限，以及邮件草稿是否有非公开/企业接口。
2. 一个专用测试租户或安全测试客户，含允许使用的测试收件箱和脱敏历史邮件。
3. 明确允许 Playwright 自动化，以及验证码、二次验证和重新登录的协作方式。
4. 第一次写入前，由用户确认测试客户、收件人、主题标记和“只保存、不发送”。
5. 完成三次证据：保存返回、草稿箱读回一致、重新登录后读回一致。

当前只读核验已确认小满网页具有邮件、客户、商机、任务和企业管理等模块；尚未执行任何真实草稿写入，也不能把当前状态称为“已打通”。
